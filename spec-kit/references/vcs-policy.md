# Version-Control Policy for `.specify/`

## Principle

Commit project intent; reconstruct installed artifacts. Catalogs and bundle declarations say *what* the project depends on; installed copies and registries are *outputs* of installation and execution. When both are committed, they drift and the repository no longer says which is true.

Three categories:

| Category | Examples | Commit? | Restored by |
| --- | --- | --- | --- |
| Project intent | constitution, `specs/`, bundle declarations, `.specify/*-catalogs.yml`, `.specify/integration.json`, `.specify/extensions.yml`, `<ext>-config.yml`, workflow overlays | yes | — |
| Installed artifacts | `.specify/extensions/*/*`, `.specify/presets/*`, `.specify/workflows/*`, installed step packages | no | `specify bundle install` (or per-kind `add`) |
| Runtime/install state | `.specify/extensions/.registry`, `.specify/bundle-records.json`, `workflow-registry.json`, `feature.json`, `local-config.yml`, caches, `.backup/`, `runs/` | no | rebuilt by the tooling |

Spec Kit's default is deliberately narrow. `specify init` scaffolds a managed `.specify/.gitignore` containing only:

```gitignore
feature.json
extensions/*/local-config.yml
```

Edits to that managed file are preserved on re-init; `specify init --here --force` restores the managed content.

## Strict policy (catalog-managed projects)

Append the rules from [../assets/specify-gitignore.txt](../assets/specify-gitignore.txt) to `.specify/.gitignore` (patterns are relative to `.specify/`; prefix everything with `.specify/` instead if you keep the rules in the root `.gitignore`).

Why each group:

- **Installed copies** (`extensions/*/*`, `presets/*`, `workflows/*`): anything catalog-derived and not edited locally. The negation `!extensions/*/*-config.yml` re-includes extension project config. The ignore pattern must target directory *contents*, not the directory, or the negation cannot work. `local-config.yml` / `*-config.local.yml` must stay ignored — re-append an explicit ignore after the negation.
- **Workflow overlays** (`!workflows/overlays/`): project-owned customizations; they live outside installed workflow dirs precisely so they survive updates.
- **Runtime state** (`runs/`, `.cache/`, `.backup/`): regenerated by the tooling.
- **Install-state records** (`.registry`, `bundle-records.json`, `workflow-registry.json`): the bundler resolves what is installed mainly through these records, not by inspecting the filesystem. Committing them while ignoring the files they describe makes a fresh clone claim components are installed when they are absent.
- `.specify/extensions.yml` is *not* install state: it is extension enablement and hook configuration, and is committed.

Locally authored packages are the one judgment call: if the project deliberately owns a package's source, keep the source outside `.specify/` (or commit it explicitly) and treat the installed copy as reconstructable.

## Fresh-clone acceptance test

A declaration is only real if a clean checkout reconstructs it:

```bash
git clone <repo> && cd <repo>
specify bundle install <bundle-id>
```

`bundle install` initializes the project on demand, so this single command is the full restore path. Then confirm installed versions match the bundle pins (`specify bundle list --json`).

If more steps are needed — manual `specify extension add` runs, remembered priorities, wiki instructions — the model is incomplete. Usually one of three things is missing: a bundle dependency, a version pin, or project-owned customization that should have been committed.

Do not test by deleting `.specify/extensions/`, `.specify/presets/`, or `.specify/workflows/` from a working checkout: that also deletes tracked intent (extension project config, overlays, installation metadata). Always clone into a clean directory.

For projects without a bundle: either re-add each component explicitly as part of the restore procedure, or package the stack as a bundle so `bundle install` is the single declaration. Prefer the bundle.

## Deliberate priorities

Composition is part of the declaration:

- Presets default to priority 10; lower wins; ties break alphabetically by id. Set explicit priorities for every installed preset.
- `replace` beats the layer below outright; `prepend`/`append`/`wrap` compose with it. Decide precedence on purpose, per template.
- Shared preambles belong in one file referenced by many preset entries, not copied into many commands.

## Checklist

- [ ] `.specify/.gitignore` contains managed lines plus strict-policy rules.
- [ ] No installed copy, registry, cache, or backup is tracked (`git status` after `bundle install` should be clean).
- [ ] Bundle declaration and pins are committed; every pin matches what is installed.
- [ ] Preset priorities are explicit; composition strategies are intentional.
- [ ] Fresh clone + `specify bundle install <id>` reaches a working state and matches the pins.
