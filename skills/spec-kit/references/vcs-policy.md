# Version-Control Policy for `.specify/`

Related docs: [guides/existing-projects](https://github.github.io/spec-kit/guides/existing-projects.html) (initializing into an existing repo), [reference/bundles](https://github.github.io/spec-kit/reference/bundles.html) (declaration semantics).

## Principle

Commit project intent; reconstruct installed artifacts. Catalogs and bundle declarations say *what* the project depends on; installed copies and registries are *outputs* of installation and execution. When both are committed, they drift and the repository no longer says which is true.

Three categories:

| Category | Examples | Commit? | Restored by |
| --- | --- | --- | --- |
| Project intent | constitution, `specs/`, project-owned bundle source (`.specify/bundles/<id>/`), `.specify/*-catalogs.yml`, `.specify/integration.json`, `.specify/extensions.yml`, `<ext>-config.yml`, workflow overlays | yes | — |
| Installed artifacts | `.specify/extensions/*/*`, `.specify/presets/*`, `.specify/workflows/*`, installed step packages, agent command/skill files outside `.specify/` (`<agent-dir>/…/speckit*`) | no | `specify bundle install` (or per-kind `add`); agent commands also via `specify init` / `specify integration install` |
| Runtime/install state | `.specify/extensions/.registry`, `.specify/bundle-records.json`, `workflow-registry.json`, `feature.json`, `local-config.yml`, caches, `.backup/`, `runs/` | no | rebuilt by the tooling |

Spec Kit's default is deliberately narrow. `specify init` scaffolds a managed `.specify/.gitignore` containing only:

```gitignore
feature.json
extensions/*/local-config.yml
```

`specify init --here --force` (the scripted variant for a non-empty checkout) **rewrites that managed file from the template — appended rules are lost**, contradicting the file's "changes are preserved" header (observed on 1.0.13). The same run re-stamps `.specify/integrations/<key>.manifest.json` with a fresh `installed_at`.

## Strict policy (catalog-managed projects)

Append the rules from [../assets/specify-gitignore.txt](../assets/specify-gitignore.txt) to `.specify/.gitignore` (patterns are relative to `.specify/`; prefix everything with `.specify/` instead if you keep the rules in the root `.gitignore`). The agent command directories outside `.specify/` need their own rules — see the next section and [../assets/agent-commands-gitignore.txt](../assets/agent-commands-gitignore.txt).

Placement follows the restore path: if re-running `specify init` is part of how a checkout gets rebuilt (see "Scaffold-restored projects" below), the rules belong in the **root `.gitignore`** — anything appended to `.specify/.gitignore` is wiped by `init --force` and the post-restore `git status` turns dirty. Appending to the managed file is only durable in projects that never re-run init.

Why each group:

- **Installed copies** (`extensions/*/*`, `presets/*`, `workflows/*`): anything catalog-derived and not edited locally. The negation `!extensions/*/*-config.yml` re-includes extension project config. The ignore pattern must target directory *contents*, not the directory, or the negation cannot work. `local-config.yml` / `*-config.local.yml` must stay ignored — re-append an explicit ignore after the negation.
- **Workflow overlays** (`!workflows/overlays/`): project-owned customizations; they live outside installed workflow dirs precisely so they survive updates.
- **Runtime state** (`runs/`, `.cache/`, `.backup/`): regenerated by the tooling.
- **Install-state records** (`.registry`, `bundle-records.json`, `workflow-registry.json`): the bundler resolves what is installed mainly through these records, not by inspecting the filesystem. Committing them while ignoring the files they describe makes a fresh clone claim components are installed when they are absent.
- `.specify/extensions.yml` is *not* install state: it is extension enablement and hook configuration, and is committed.

Locally authored packages are the one judgment call: if the project deliberately owns a package's source, keep the source outside `.specify/` (or commit it explicitly) and treat the installed copy as reconstructable. The project-owned bundle source (`.specify/bundles/<id>/`, see below) is the one hand-authored tree that lives inside `.specify/` on purpose — the strict rules do not touch it.

## Agent command directories (outside `.specify/`)

`specify init` and component installs also write the agent's command or skill files **outside** `.specify/`: `.pi/prompts/speckit.plan.md`, `.opencode/commands/speckit.specify.md`, `.claude/skills/speckit-plan/SKILL.md`, `.github/agents/speckit.plan.agent.md`, and so on. They are installed artifacts, not intent:

- every generated command file is recorded with a content hash in `.specify/integrations/<key>.manifest.json`;
- the same preset output is rendered byte-identically into each installed integration;
- extension commands land there too (`speckit.bug.*`, `speckit.wireframe.*`) and are **not** in the integration manifest, so the manifest alone does not enumerate them.

Ignore them in the **root `.gitignore`**, never in `.specify/.gitignore`: a subdirectory `.gitignore` cannot match paths outside its own directory (`../.pi/prompts/` has no effect), and `specify init --force` rewrites the managed file anyway. Use [../assets/agent-commands-gitignore.txt](../assets/agent-commands-gitignore.txt). The patterns are prefix-scoped (`<agent-dir>/<commands-subdir>/speckit*`) rather than whole-directory ignores, so hand-written prompts and third-party skills in the same directories stay visible.

Keep the list in sync with `.specify/integration.json`: add the matching line when you install an integration. For an integration that is not in the asset (a new integration, or `generic` with a custom `--commands-dir`), read the generated paths from `.specify/integrations/<key>.manifest.json` and add the line for their directory:

```bash
python3 - <<'PY'
import glob, json, os
for f in glob.glob(".specify/integrations/*.manifest.json"):
    for path in json.load(open(f))["files"]:
        if not path.startswith(".specify/"):
            print(os.path.dirname(path) + "/speckit*")
PY
```

### Skills installed by other tools

`.claude/skills/`, `.agents/skills/`, `.opencode/skills/`, … are shared directories. Spec Kit only owns the `speckit*` entries in them. Everything else — for example the `cockpit-run-context` skill a TUI installs at start — is not classified by this policy: commit it or ignore it, but decide explicitly. Never ignore a skills directory as a whole.

### Agent config files are not artifacts

Integration setup also *merges* into shared agent config — `.claude/settings.json`, `.vscode/settings.json`, `opencode.json`, `.codex/config.toml`. Those files carry project or machine configuration and must stay visible; the `speckit*` pattern deliberately does not match them. The integration-owned exception is Copilot's `.github/hooks/speckit.json`.

## Scaffold-restored projects (no bundle)

Some projects also ignore the init-scaffolded core (`.specify/scripts/`, `.specify/templates/`) and rebuild everything with one `specify init` command instead of a bundle:

- The strict rules live in the **root `.gitignore`** with `.specify/` prefixes, plus `.specify/scripts/*`, `.specify/templates/*`, and `.specify/integrations/*.manifest.json` (init re-stamps `installed_at`, so a tracked manifest turns up modified after every restore).
- `.specify/.gitignore` is committed exactly as scaffolded (managed-only), so a refresh produces no diff.
- Restore and acceptance in one step:

  ```bash
  specify init --here --force --non-interactive --integration <agent> --script sh [--preset <id>]
  ```

  Expected afterwards: `.specify/scripts`, `.specify/templates`, installed presets/workflows, and the agent commands are back (ignored by the root-level `speckit*` rules); `git status` is clean.

- Multi-integration projects need one extra step: `specify init --force --integration <agent>` collapses `.specify/integration.json` to that one integration (observed on 1.0.13), so re-run `specify integration install <other>` for the rest and commit the restored `integration.json`. Each installed integration still needs its `speckit*` line.

## Project-owned bundle (`.specify/bundles/<id>/`)

A project with more than one component declares its stack once, as a committed bundle source:

```text
.specify/bundles/<project>/
├── bundle.yml     # the pinned Spec Kit components this project depends on
└── README.md      # the stack this repo pins + the command that restores it
```

`bundle.yml` carries the bundle `id`, a SemVer `version`, and one pinned entry per component; bump the
version on every manifest change. The README states the pinned stack and its restore command
(`specify bundle install .specify/bundles/<project>`); `bundle build` requires the file.

```bash
specify bundle validate --path .specify/bundles/<project>
specify bundle install .specify/bundles/<project>              # restore, idempotent
specify bundle install .specify/bundles/<project> --refresh     # apply manifest edits
specify bundle build --path .specify/bundles/<project> --output <dir>   # only when publishing
```

Why a declaration instead of remembered `add` commands:

- The declaration is reviewable and diffable; a runbook of `specify extension add …` calls is neither and drifts silently.
- `.specify/bundle-records.json` records what was installed but **not** the source it came from, so it cannot restore anything by itself. `specify bundle install <id>` only works for a catalog bundle — a project-owned bundle is always restored by path.
- `specify <kind> add` is for experiments; the restore path is always `bundle install`.

What a local source does and does not change: the **manifest** resolves locally, without consulting the catalog stack, so it works offline and depends on no catalog's install policy. The **components** are installed exactly as `specify <kind> add` would install them — bundled assets work offline, catalog components need an install-allowed catalog, and a discovery-only pin is still refused. Point the pins at components your catalogs allow.

A changed manifest against an existing record is refused until you pass `--refresh` (which re-applies owned components and drops ones no longer declared). `bundle build` is output: without `--output` the artifact lands next to `bundle.yml`, where `bundles/*/*.zip` ignores it.

## Fresh-clone acceptance test

A declaration is only real if a clean checkout reconstructs it:

```bash
git clone <repo> && cd <repo>
specify bundle install .specify/bundles/<project>   # project-owned bundle source
# or, for a catalog bundle:
specify bundle install <bundle-id>
```

`bundle install` initializes the project on demand, so this single command is the full restore path. Then confirm installed versions match the bundle pins (`specify bundle list --json`) and that `git status --short` is empty — agent command directories included.

If more steps are needed — manual `specify extension add` runs, remembered priorities, wiki instructions — the model is incomplete. Usually one of three things is missing: a bundle dependency, a version pin, or project-owned customization that should have been committed.

Do not test by deleting `.specify/extensions/`, `.specify/presets/`, or `.specify/workflows/` from a working checkout: that also deletes tracked intent (extension project config, overlays, installation metadata). Always clone into a clean directory.

For projects without a bundle: either re-add each component explicitly as part of the restore procedure, or declare the stack as a project-owned bundle (see [Project-owned bundle](#project-owned-bundle-specifybundlesid)) so `bundle install` is the single declaration. Prefer the bundle. For scaffold-restored projects the single command is the `specify init --here --force` line above — same acceptance: it runs, the agent commands are present, `git status` is clean.

## Deliberate priorities

Composition is part of the declaration:

- Presets default to priority 10; lower wins; ties break alphabetically by id. Set explicit priorities for every installed preset.
- `replace` beats the layer below outright; `prepend`/`append`/`wrap` compose with it. Decide precedence on purpose, per template.
- Shared preambles belong in one file referenced by many preset entries, not copied into many commands.

## Checklist

- [ ] Strict rules are placed deliberately: in `.specify/.gitignore` (only if init is never re-run) or in the root `.gitignore` (when `specify init --force` is the restore path).
- [ ] If init is the restore path: `.specify/.gitignore` stays managed-only and `.specify/integrations/*.manifest.json` is ignored.
- [ ] No installed copy, registry, cache, or backup is tracked; `git status` is clean after `bundle install` and after a scaffold restore — agent command/skill directories included.
- [ ] Agent command directories are ignored in the root `.gitignore` ([../assets/agent-commands-gitignore.txt](../assets/agent-commands-gitignore.txt)), not in `.specify/.gitignore`; every installed integration has a matching line.
- [ ] Bundle declaration and pins are committed (`.specify/bundles/<id>/`, or a catalog bundle id); every pin matches what is installed.
- [ ] The bundle source is tracked while its artifact is not: `git check-ignore -v .specify/bundles/<id>/bundle.yml` stays silent and no `bundles/*/*.zip` is committed.
- [ ] Preset priorities are explicit; composition strategies are intentional.
- [ ] Fresh clone + `specify bundle install .specify/bundles/<id>` (or `bundle install <id>` for a catalog bundle) reaches a working state and matches the pins.
